本次修改说明：不同起点、固定检测判定、成功即停止

这次修正的是实验起点设计。上一版十个AND session虽然调用了十次attacker，实际却生成同一份网表；一次被缓存的漏检就让三种反馈全部在第一轮结束。这既不是十份不同电路，也没有测试到反馈的作用。

现在每种电路预先固定十份不同配置，运放覆盖9种“插入位置×实现方式”组合，AND覆盖6种，再无放回补足十份。抽样只读取合格菜单，不读取检测结果。配置、抽样seed、源代码和控制电路在新API请求前冻结。

第一轮由Python按上述配置生成，不调用attacker。第二轮起才由LLM提出下一份配置。第一轮仍计入每session最多十次的上限，三种反馈共享同一session的起点与判定。因此当前实验测量的是从指定起点出发的反馈辅助搜索，不能把第一轮成绩称为LLM一次生成成功率。后续候选仍可能重复。

继续严格执行的规则
1. 每条session首次电气有效且detector判定is_trojan=false就停止；失败最多十次。
2. Attacker temperature=0.3；detector=0.0、seed=410001。相同请求跨session/条件复用首次有效判定，不能靠重复提交碰运气。
3. 两种电路×三种反馈×每组十条session，共60条；统一统计，不分batch。
4. 只保留一张六组结果表和累计逃逸session折线图，没有增加补充对比实验。
5. 先用两份干净电路和两份已知木马做基本验收，四项全部通过才运行主实验。这四份控制与正式菜单的精确网表不重合，但共用电路构造，不能据此声称检测器准确率100%。控制不进入session分母或曲线。
6. 反馈规则不变：None从第二轮起每次使用全新请求；Binary/Full只收到自己上一轮配置和对应布尔/完整检测反馈，不收到仿真结果，也没有跨session记忆。

运放 / None：6/10 → 6/10

运放 / Full：6/10 → 10/10

AND / Binary：4/10 → 10/10
AND / Full：4/10 → 10/10

现在AND的六个被抓起点确实进入后续修改；运放则有四个。Binary与Full最终都完成逃逸，Full在本次运行中更早达到十个成功session：运放第5次、AND第3次；Binary分别第6次和第7次。None没有新增成功。运放三组“成功session首次成功次数的中位数”都为1，因为六个共享起点已经成功；不能用这个中位数说三组修改速度相同，需要看完整曲线。

为何不能直接把新旧变化全归因于这次改动
检测温度和seed没有改过，也没有挑选seed。但重新建立缓存后，旧版重复的AND网表（output_shunt / mosfet / p2 / medium）从旧判定false变为新判定true，两个请求载荷完全相同。对保存记录的来源核查还发现两个重叠opamp请求从true变为false。temperature=0与seed并不保证API跨次调用完全一致。缓存只保证本次运行内部对相同输入保持同一判定。因此新旧结果同时涉及起点设计改变和新缓存首次判定变化，不能当作只改变起点的因果对照，更不能解释为模型进步。旧记录完整保留，但不进入当前表格。

数据完整性
157个实际候选事件由20个预设起点和137个LLM提案组成；197条条件级记录的差额40来自共享起点。157个事件全部通过正常功能和触发测试。正式候选去重后44份网表，各获得一次新判定，其余113次跨候选复用。实际API调用185次：137次attacker、44次正式detector、4次控制detector，全部得到有效输出，没有截断或拒绝。25项离线协议测试通过。独立审计通过：逐项核对原始响应、波形、判定复用、停止位置、所有session与曲线，无成功后的额外尝试。

报告修改范围
标题、作者、Introduction、原验证段和反馈段保持合作者已修改的措辞。方法段开头只把“First, the attacker receives”改成“After the first attempt, the attacker receives”，以纠正第一轮现在没有attacker调用这一事实。其余修改针对新的起点、基本验收、统计及解释。报告不写个人预算、密钥设置或沟通历史。
